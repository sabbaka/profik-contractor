# Localisation

The app ships in English and Czech. A Czech contractor must never see an English
word that is ours — only their own data, and the exceptions listed at the bottom.

## The rule

All user-facing copy goes through `useTranslation()` and lives in
`src/i18n/locales/en.json` **and** `cs.json`. Add both in the same change; a key
in one file only is a bug, not a to-do.

Counted strings use i18next plurals, and Czech needs three forms:

```json
"offersBadge_one":   "{{count}} nabídka",
"offersBadge_few":   "{{count}} nabídky",
"offersBadge_other": "{{count}} nabídek"
```

Keys extend the namespace that already covers the area — `job.*`, `offer.*`,
`profile.*`, `map.*`. Look before inventing one.

## Copy that is not a string literal

Three shapes are easy to miss, and all three have been found in these apps:

**Labels in a lookup map.** Keep the **key** in the map, not the copy, and
resolve it where `t` is in scope. Colours and other data stay put:

```ts
const STATUS_LABEL: Record<StatusKind, string> = {
  open: "status.open", // key, not "Open"
};
```

**Helper functions that build copy.** A module-level helper has no `t`. Return a
key and let the caller translate it.

**Option arrays declared at module level.** They are evaluated at import time,
where `t` does not exist, and options frozen then keep the old language after
the user switches it. Build them inside the component with `useMemo(..., [t])`.
This one looks fine in review and only breaks when someone changes language.

## Dates and numbers

Never hardcode a locale — `toLocaleDateString("en-US", …)` gives a Czech user
American dates whatever the interface says. Derive the tag from
`i18n.language`.

Prices are the deliberate exception: `formatCzk` in `src/utils/currency.ts`
always formats in Czech style, because the app bills in CZK and the format
follows the currency, not the reader. Its manual formatting is also on purpose —
Hermes' `Intl` returns "Kc" instead of "Kč" on iOS.

## Deliberately left in English

Do not "fix" these:

- **Job titles and categories** written by the client app. They are data, stored
  in the database, and the client's language is not the contractor's.
- **`__DEV__` labels and dev-only alerts.** Nobody outside the team sees them.
- **The brand** — "Profik Pro".

## Country is stored as a code, not a name

`Job.country` holds an ISO 3166-1 alpha-2 code (`CZ`), because a name has a
language and the column used to hold both "Czechia" and "Česko" for the same
country. The backend normalises whatever it is sent; the label is chosen here,
at display time:

```ts
formatCountry(job.country, t)   // src/utils/country.ts
```

It reads `job.country.<CODE>` from the locale files and falls back to the code
itself when there is no key, so an unmapped country shows "SK" rather than a
blank. Add the key rather than relying on the fallback.

Both display sites go through it — `ContractorJobCard.tsx` and
`detail/JobLocation.tsx`. The client app carries the same helper in
`src/features/jobs/utils.ts`; keep the two in step.

## Screen-reader labels are copy

`accessibilityLabel` never appears on screen, which is exactly why it gets
written in English and stays that way. It goes through `t()` into `a11y.*` in
both locale files like any other string. The checker flags a hardcoded one.

## The checker, and what it cannot see

`npm run i18n:check` (`scripts/check-hardcoded-strings.mjs`) fails the build on
hardcoded copy and runs in CI. It is the same script as the client app's; fix a
false positive in both or they drift.

Trust it for literals, and only for literals. It reads whole files, so it sees
multi-line JSX, but it is a regex over text. **It cannot see copy assembled at
runtime** — a label in a map, a string from a helper, a template literal, a key
built by interpolation. Those are exactly the three shapes above, and the
checker will call a file clean while every one of them is still English.

So when you finish an area, open it and switch language. A screen that stays
English under a green check is the normal failure here, not an unusual one.

Genuine exceptions go in `ALLOWED` or `SKIP_FILES` in the script, with a comment
saying why — an exception without a reason is indistinguishable from an
oversight.
